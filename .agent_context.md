# Project context

## Domain documentation

Public user documentation lives in `docs/`. Completed artifact-contract work items retain their canonical specifications. Older internal design notes may exist in a local, Git-ignored `.archive/`; they are superseded, may be stale, and tracked work must not depend on them. Verify behavior against the code.

In conceptual documentation, refer to “an LLM” rather than the Low, Medium, or High model tier. Explain what the LLM does and why the step is valuable; keep model-tier and configuration details in settings guides or technical reference documentation.

## Documentation style

Apply these conventions to all public documentation in `docs/` and to the README's documentation links:

- **Record nouns:** Capitalize **Campaign**, **Session**, **Player**, **Role**, and **Glossary** when they mean the TableSage record ("open the Campaign", "each Session", "a Player's voice print"). Keep them lowercase when used as modifiers or in ordinary phrases ("campaign history", "campaign glossary", "session outputs", "session summary", "player-ready"). Filenames, code, and paths stay as they are.
- **Headings and page titles:** Use Title Case. Keep short articles, conjunctions, and prepositions (a, an, the, and, or, to, of, in, on, for, with, from) lowercase unless they are the first word.
- **Screen names:** Use Title Case consistently: Welcome, Settings, Campaigns List, Campaign Detail, Players List, Player Detail, Session Detail, Process Session, Export Artifact. Write button, dialog, step, and action names exactly as the app shows them, in bold.
- **Voice print, not voice profile:** A Player's voice print is the single term for what TableSage knows about their voice. Never use "voice profile" in the UI, documentation, or code; write "voice print" wherever it would appear. Voice samples are the audio clips a voice print is computed from.
- **Link text:** Index lists and "See [Page]" references use the linked page's exact title. Links inside a sentence may use natural wording.

## Markdown formatting

Do not hard-wrap documentation Markdown to a fixed line length. Keep each prose paragraph on one source line and let the editor wrap it visually. Keep each list item's prose on one source line where possible. Preserve line breaks required by Markdown structure or meaning, including paragraph boundaries, headings, separate list items, tables, code blocks, and intentional hard line breaks.

## TTRPG reincorporation

Reincorporation brings an established campaign element back into play so that it gains renewed relevance. It is strongest when the element either acquires new meaning or gains new utility:

- **New meaning:** Later context changes the nature of the element or the players' understanding of it.
- **New utility:** Players use the element as a tool or resource in a later situation.

Favor opportunities that let players discover and initiate an element's new utility themselves; this turns continuity into player agency. Support changes in meaning with established facts so they feel earned rather than like arbitrary twists, and do not force every earlier detail to return. Emotional or thematic callbacks are also valid reincorporation even when they provide neither transformation nor practical utility.

## Settings

Whenever you add code where `tablesage-tui` (directly, or via `tablesage-application`) calls into `tablesage-tools`, any tunable knob for that call must be read from the TUI's deployed `settings.yaml` (`AppSettings`, loaded by `tablesage_model.setup.ensure_settings` and injected into `Application` at `tablesage_tui.screens.main_app.main`'s composition root) rather than hardcoded.

The settings-agnostic boundary is `tablesage-tools` itself: it only ever receives plain values (`float`, `int`, etc.), never an `AppSettings` object or one of its sections: tools operate on generic inputs and explicitly supplied paths, and do not know about campaigns, players, the application's filesystem layout, or `AppSettings`. `tablesage-application` (including `session_pipeline`) is not bound by that rule — it may accept `AppSettings` section objects (for example, `TranscriptionAndDiarizationSettings`) directly as parameters, unpacking them into plain values only at the calls it makes into `tablesage-tools`.

The packaged default lives at `apps/tablesage-tui/src/tablesage_tui/resources/settings.yaml`; add new knobs there and to `RemoveOutliersSettings`-style sections of `AppSettings` in `tablesage_model.settings`, following the `remove_outliers` precedent used by the voice print clean-up path.
