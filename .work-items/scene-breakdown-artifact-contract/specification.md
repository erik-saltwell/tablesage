# Scene Breakdown and Recap

Scene Breakdown is a compact, machine-readable account of every scene in one session. It supports recap generation and campaign-scale reading without sending complete Ledgers. The [design discussion](../../.documentation/designs/scene-breakdown/design.md) records the product decisions; this specification defines their implementation.

## Joint generation and source boundaries

One LLM call reads the routed Role Transcript and returns exactly three fields:

```json
{
  "starting_situation": "The shared opening situation.",
  "ledger": {"utterances": []},
  "scene_breakdown": {"ending_situation": "The situation at the end.", "scenes": []}
}
```

The starting situation uses only Starting Context. Ledger entries and scene events use current Session Utterances. Scene context may refer to the shared starting situation; opening recap and introduction content is excluded. Titles, locations, and signature details can preserve appropriate phrases spoken in the current session even if those phrases do not appear in the condensed Ledger. Scene outcomes must agree with the Ledger, retaining accepted corrections, uncertainty, and the distinction between plans and completed actions. A glossary supplies spelling, not additional events.

## Persisted schema

`scene_breakdown.json` is strict JSON validated by Pydantic. Unknown fields are rejected. Text is trimmed and nonempty. It contains:

| Field | Type / meaning |
| --- | --- |
| `version` | `1` |
| `session_id`, `session_name` | Application-owned Session identity |
| `starting_situation` | The exact generated starting situation also placed in Ledger v4 |
| `ledger_sha256` | Generation-time provenance: SHA-256 of the `ledger.json` bytes produced in the same run |
| `ending_situation` | Established situation at the end, including what remains unresolved |
| `scenes` | Ordered list of scenes |

Each scene contains:

| Field | Type / meaning |
| --- | --- |
| `title` | Recognizable short label; use spoken phrasing when appropriate |
| `location` | One recognizable location, or `null` when unknown |
| `participants` | List of relevant characters/entities |
| `situation` | Immediate problem or interaction, including an explicit goal when supported |
| `outcome` | What happened, including unresolved or interrupted results |
| `carry_forward` | String list of durable discoveries, commitments, consequences, and explicitly established clocks or time pressure; may be empty |
| `signature_detail` | Required, nullable sensory, thematic, or personal memory cue that distinguishes this scene; never invented to fill the field |
| `ledger_ranges` | Nonempty list of inclusive zero-based `{start_index, end_index}` references to Ledger utterances |

A scene is a coherent interaction or problem, not necessarily a location. Combine a continuing interaction interrupted by cutaways. Order scenes by their first Ledger entry and each scene's ranges by start index. Ranges must be in bounds and partition every Ledger entry exactly once, without gaps or overlaps; interleaving uses multiple noncontiguous ranges. All scenes are represented, although scene text need not repeat every assigned Ledger fact. An empty Ledger requires an empty scene list; the ending situation may repeat the starting situation.

## Persistence and lifecycle

Canonicalize generated scene and range ordering by first Ledger index, without changing assignments. Validate the complete joint response before persisting. Structural failures retry up to three attempts with validation feedback; candidates are accepted or rejected as pairs. Application metadata and the Ledger digest are never model-generated.

Stage the Ledger JSON, Ledger Markdown, and Scene Breakdown before replacing files. Their replacement forms one rollback unit. Handled failures restore prior bytes. A `.ledger-generation-incomplete` marker remains after a process interruption or failed rollback; readiness and export listings suppress the pair and derived outputs until successful regeneration. This is recoverable multi-file replacement, not a filesystem-wide atomic transaction.

Ledger and Scene Breakdown are sibling outputs of the same build step rather than freshness dependencies of one another. Upstream changes make the shared step stale and regenerate both; hand-editing one sibling only makes its actual downstream consumers stale. `ledger_sha256`, shared metadata, and Ledger ranges describe their joint generation and are not revalidated against a subsequently hand-edited Ledger. The registry category is `FROM_TRANSCRIPT`, filename is `scene_breakdown.json`, and `should_show_in_ui=False`; no Markdown companion is created. A missing sibling makes the shared step incomplete, while an interrupted replacement instructs the user to regenerate.

## Recap and detailed Summary

The existing `recap_summary.md` is generated by an LLM using only Scene Breakdown as its narrative source, plus existing metadata, attendees, and glossary orientation. Python validates the Scene Breakdown itself before calling the recap model; it does not require the current Ledger bytes to match generation-time provenance. The model does not receive the Ledger. The prompt selects essential continuity and useful signature details rather than listing every scene. It targets 180 words, at most 240 words and six bullets. These length limits are prompt instructions and optimizer metrics, not production rejection criteria.

The packaged Generate Recap Summary `system.md` is a build dependency of `recap_summary.md`.
Changing it makes the recap stale and propagates to following-session Summaries that consume it.

Production validates nonempty flat `- ` Markdown bullets with no headings, nesting, continuation prose, or fences, retrying malformed content up to three times. The application adds `## Recap` and atomically replaces the existing recap artifact. Provider errors fail immediately; failed generation preserves the previous recap.

Detailed `summary.md` continues to use the current Ledger. Composition inserts the previous session's recap and the current session's Player Introductions, using the existing marker validation and atomic persistence. The first session has no previous recap. Regenerating a recap makes the following session's existing Summary stale; `Generate Outputs` for that following session rebuilds it.

Implementation: [scene_breakdown.py](../../packages/tablesage-application/src/tablesage_application/session_pipeline/scene_breakdown.py), [generate_ledger.py](../../packages/tablesage-application/src/tablesage_application/session_pipeline/generate_ledger.py), [generate_recap_summary.py](../../packages/tablesage-application/src/tablesage_application/session_pipeline/generate_recap_summary.py).

## Campaign-aware Previously On export

The application also exposes a read-only Campaign Scene Recap. It brackets every Scene from
every current Campaign Scene Breakdown with the first Session's `starting_situation` and the
last Session's `ending_situation`. Scenes are flattened in Session sequence and then Scene-array
order without Session metadata, keeping the representation compact. The view uses the same
freshness, completeness, interruption-marker, and schema validation as the Previously On history
snapshot; it is not persisted and does not affect artifact invalidation.

The external Previously On workflow consumes validated current Scene Breakdowns from every
Campaign Session. It uses the existing freshness graph, paired-output completeness, and interruption
marker checks without changing the persisted schema or comparing against hand-edited Ledger bytes.
Session UUID plus zero-based Scene index identifies sources within its in-memory snapshot.
The highest-sequence Session's `ending_situation` initializes the editable opening situation.

An ingredient generator and scout receive complete Campaign breakdowns. After GM selection, a
separate editor receives only the selected Scene records in chronology, edited starting situation,
and glossary spelling/identity guidance. Its complete Markdown is saved verbatim to an external
GM-chosen file with atomic replacement, without output validation, count limits, managed artifact
registration, or downstream invalidation. This is separate from `recap_summary.md` above.
