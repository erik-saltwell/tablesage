# Automated Pipeline Reviews: Intent

## Intended Outcome

Run an automated review of the [Unified Matters Pipeline](../unified-matters-pipeline/): its prompts and the Session Summaries generated by its most recent run. The review gives a first check of what is currently suboptimal in the prompts and Summaries, judged against the user's recorded learnings in [`learnings/`](../../learnings/README.md).

The review has two consumers:

- **The user**, reading it to see where the pipeline currently stands.
- **An agent**, which may be asked to iterate on the pipeline until it passes all review checks.

## Two Skills

The user plans two skills, registered for both Claude and Codex:

| Skill | Input | Output |
|---|---|---|
| `extract-learnings` | The `learnings/` collection: preferences, approaches and examples | A **review guide**: the list of things to check for or against |
| `review-pipeline` | The review guide, plus the prompts and generated Session Summaries of the last unified pipeline run | A **review** |

Splitting the work this way keeps the learnings as evidence, as the [learnings README](../../learnings/README.md) intends, and turns them into checks in a separate step. The review then runs against the distilled guide rather than the raw collection.

## Settled Meanings

The user clarified these on 2026-11-01:

- **Last run:** the highest-numbered experiment pass under [`experiments/session-004/`](../unified-matters-pipeline/experiments/session-004/) (currently `pass-9`), meaning both its prompts and its generated outputs. It is not the phone-review copy in `deployment/unified-review/` or a future production `unified/` Session folder. The project has no production `generate-unified-matters` command yet.
- **What is reviewed in the outputs:** only the Session Summary (`summary.md`), not the Table Recap.
- **Pass and fail work in both directions:** output fails a check if it matches a negative pattern in the review guide. It also fails if it lacks a positive pattern the guide expects.

## Prompt Checks

The first prompt check looks for cases where examples or guidance in the prompts are **overtuned to the user's test Sessions**. The review must also make room for other prompt checks later; overtuning is the first, not the only one.

The prompts live in the pass's `prompts/` folder, one folder per step (for pass 9: `step1_scenes`, `step2_threads`, `step2c_changes`, `step3_facts_homes`, `step3r_resources`, `step4_stopping`, `step6_writing`, `step8_recap`).

## Summary Checks

The review applies the guide's positive and negative patterns to each generated Session Summary. In pass 9 these are `runs/s001/summary.md` and `runs/s002/summary.md`. A run may cover all four test Sessions or fewer, and the review covers whichever Summaries the run produced.

## Review Output

The review is Markdown written in the chat thread, not saved as a file. It is structured as follows:

1. **Prompt checks** section.
2. **Summary checks** section, with:
   - one subsection for each Session Summary reviewed;
   - inside each of those, first an **Across the Summary** subsection for checks that span headings or compare with the previous Session's Summary (added in the 2026-11-01 workshop; see [idea.md](idea.md#2-an-across-the-summary-subsection));
   - then one subsection for each heading of that Summary as written: for example *Last session...*, *Your goals*, *What could help*, *Still unanswered*, *Meanwhile* and *Where you are*.

The learnings are organized by the older Matter categories (Revelations, Mysteries, Goals, and so on), but the review is organized by the Summary's own headings.

To keep the review readable, it shows only failures and issues (`FAIL`, `NOT MET` and `ADVISORY`), and only the sections and subsections that contain one; sections where everything passed are left out (user decision, 2026-11-01). One header line still names any check that could not be applied, such as a comparison with a previous Session the pass lacks.

## Check Kinds

Settled in the 2026-11-01 workshop; the reasons are in [idea.md](idea.md):

- **Pattern checks** apply to any Session and can fail it.
- **Session-specific expectations** (goldens, expected findings, known-bad lines) are checked only against their own Session, labelled as such and counted separately. A current expectation that is not met is also a failure: the user declined the option of making them informational only. They are also the input to the overtuning prompt check.
- **Currency gate:** an entry can fail a check only if it has a `good`, `bad` or `missing` verdict, an unsuperseded preference, a definition that still applies in the unified pipeline, and no overriding decision. Other entries are **advisory**: shown with their reason, never failing.

## Constraints and Context

- The learnings are evidence, not current instructions ([learnings README](../../learnings/README.md)). Their examples carry **Spot it** checks and verdicts (`good`, `bad`, `borderline`, `missing`, `contested`), and the review guide is derived from these.
- Work on Summaries or their replacements must follow [`learnings/maintenance.md`](../../learnings/maintenance.md), per the project's agent context.
- A project skill convention already exists: `regen-campaign` lives in `.agents/skills/` and is symlinked from `.claude/skills/`. This is an observation, not a decision about where the new skills go.

## Quality Rubric

Approved by the user on 2026-11-01. It is qualitative: each dimension is judged in plain words, with no scores, scales, weights or thresholds. This follows the user's `define-rubric` skill rather than the workflow's numerical-rubric convention.

**Subject:** the automated review capability, meaning the review guide produced by `extract-learnings` and the review produced by `review-pipeline`. **Intended effect:** a trustworthy first check of the unified pipeline that the user can read and an agent can act on.

1. **Faithfulness to the learnings:** the guide's checks say what the user actually judged. They keep each verdict's status (`good`, `bad`, `borderline`, `missing`, `contested`), add nothing the user has not judged (unjudged observations stay out), and leave out nothing important.
2. **Detection accuracy:** the review finds the negative and positive patterns that are really present, or really missing, in a Summary or prompt. It raises no false alarms and gives no credit that isn't earned.
3. **Generality of checks:** each check describes the underlying pattern rather than wording from one Session. It still applies to Sessions and outputs it was not drawn from, and an agent iterating on the pipeline cannot satisfy it by changing surface phrasing.
4. **Grounded evidence:** each finding quotes the output it judges and cites the guide entry and learnings IDs (`EX-###`, `PREF-###`) it rests on, so a reader can verify it without re-deriving it.
5. **Actionability:** someone reading a finding, the user or an agent, can tell what is wrong and what kind of change would address it. The review does not need to say which pipeline step or prompt caused the problem.

Dimensions 1 and 3 can pull against each other: a faithful check may be tied to the Session it came from. Extensibility (adding new checks without reworking the skills) was proposed and dropped by the user. It remains a goal of the design, but it is not a quality dimension.
